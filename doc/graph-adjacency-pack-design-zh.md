# 图存储层 v2 设计：一个顶点两个 KV（邻接表打包 + 条件写）

English: [graph-adjacency-pack-design-en.md](graph-adjacency-pack-design-en.md)。

状态：**已实施**（2026-11-18，G1–G6，随 **8.0.0**；当前仓库随 8.1.0；实现对账见 §14）。取代
[graph-layer-design-zh.md](graph-layer-design-zh.md)（下称 v1）的盘上布局与写路径；
v1 的遍历算法、OLAP 物化层、etype 注册、API 外形保留。

依赖一项引擎能力：**原子批的条件写**（按 key 的 LSN 判断）。作为下游反馈提交
（libbitcask `feedbacks/2026-11-17-conditional-atomic-batch.md`），上游在 **8.0.0**
（S46）发布：`Cask::BatchOp::expect`（`kAbsent` / `kOrdEquals`）+ `expect_ord` +
`kCheck`，冲突返回 `kConditionFailed`，`BatchOutcome` 回报失败 op 下标与各 op 的
LSN。当前仓库子模块为 8.1.0（`13322bd`），NIF / 门面形态见 §5.3。

---

## 1. 动机

v1 是「一条边三个 key」：

| v1 家族 | 每条边 | 说明 |
|---|---|---|
| `e` src·etype·dst·rank | 1 个 key | 出边，值 = 边属性 |
| `ei` dst·etype·src·rank | 1 个 key | 反向导航，值空 |
| `et` etype·src·dst·rank | 1 个 key | 按类型列边，值空 |
| `deg` / `degi` | 每（顶点, etype）各 1 个 key | 每次加 / 删边重写 |

插入一条新边写 5 条记录、常驻 3 个 key。libbitcask 的 keydir 每个 key 常驻内存，OKI
也各有一行，所以 **key 数量 ≈ 3 × 边数** 直接决定内存与 merge 工作量。5000 万条边就是
1.5 亿个 key。

v2 的目标：**key 数量与顶点数成正比，不与边数成正比。**

## 2. 一句话模型

```
n <vid>   → 顶点内容（不变：DocValue，走 put_doc，BM25 / 向量照旧）
a <vid>   → 该顶点的邻接表（出边段 + 入边段 + 度数），一个 value
```

**一个顶点两个 KV。** 邻接表超过阈值的顶点（hub）把大的那一组拆成若干块，块是附加
的 KV（§4.3）；真实图大多幂律分布，绝大多数顶点不会触发。

顶点内容与邻接表**不合并**成一个 KV：`n` 走 `put_doc`，每次重写都会重新分词 / 重建
向量索引项，加一条边不该付这个代价。

| | v1 | v2 |
|---|---|---|
| key 数量 | V + 3E + 计数键 | 2V + hub 的块数 |
| 取一个顶点的邻居 | OKI 前缀 range + 逐条回查 | **一次点查、一次 pread**（hub：头 + 按块目录逐块点读） |
| 一跳内一致性 | per-key 弱一致 | **原子快照**（hub：可选校验，§7.3） |
| 度数 | 额外计数键，读-改-写 | 邻接表头部自带，随边原子更新 |
| 插入一条边 | 追加 5 条小记录 | 重写两端顶点的邻接表（各 ≤ 约 4 KiB） |
| 并发写同一顶点 | 计数可能不准 | 条件写冲突 → 重试，不丢边 |
| 单条边点查 | O(1) keydir | 读邻接表 + 组内二分 |
| 按类型列全库边 | `et` 前缀 range | 扫 `a` 家族过滤，或走物化层 |

## 3. 取舍先说清楚

v2 是「读更便宜、内存更省、写更贵」的交换：

- **写放大上升**。v1 单边写约 300 B 日志；v2 单边写重写两个邻接表，平均度数 50 的
  简单图约 2 × 1 KB，上限约 2 × 4 KiB（分块阈值封顶）。日志只追加，垃圾产生更快，
  merge 更频繁。批量接口（§6.4）按顶点聚合，每批里每个顶点只写一次，能挽回一部分
  （实测见 §14.3）。
- **每次写边都是读-改-写**，必须有并发保护。v2 用引擎条件写（§5），冲突时重试。
  热点顶点上大量并发单边写会反复重试——这种负载应走批量接口或事务层。
- **失去 `et` 索引**。`edges_by_type` 变成 O(V + E) 扫描。需要高频使用再加可选索引。

如果负载是「海量并发单边写、很少读」，v1 更合适。v2 面向的是读多写少、批量装载、
内存敏感的图——也是这个库目前的主要用法。

## 4. 盘上契约

### 4.1 Key 家族

| 家族 | key | 值 |
|---|---|---|
| `n` | `<G> "n" <vid:64>` | 顶点内容（不变） |
| `a` 头 | `<G> "a" <vid:64>`（13 B） | 邻接表头（§4.2） |
| `a` 块 | `<G> "a" <vid:64> <dir:8> <etype:32> <other:64> <rank:64>`（34 B） | 一块条目（§4.3）；key 里的 (other, rank) 是该块的**下界** |
| `p` | `<G> "p" <src:64> <etype:32> <dst:64> <rank:64>` | 超过内联上限的边属性（§4.4） |
| `t` / `tn` | `<G> "t" …` / `<G> "tn" …` | etype 注册表（记录体不变） |
| `g` | `<G> "g"`（5 B） | 图元信息：`<<LayoutVer:8, …>>` = 1 |

`<G>` 是图层全局前缀 `<<16#01, "_g:">>`（4 B），避免图层 key 与应用 KV、全文/向量
索引 key 撞名。

多字节整数一律大端定宽（与 v1 相同：字典序 = 数值序）。`dir`：0 = 出，1 = 入。
头 key 是同顶点全部块 key 的前缀，`<G> "a" <vid>` 的前缀 range 恰好取回「头 + 全部块」，
且头排第一。

### 4.2 邻接表头的值

```
Head   = <<Ver:8 = 1, NGroups:16, Group × NGroups>>
Group  = <<Dir:8, GFlags:8, Etype:32, Count:64, Body>>          %% 按 (Dir, Etype) 升序
GFlags : bit0 has_rank   该组有条目 rank ≠ 0
         bit1 has_props  该组有条目带属性
         bit2 chunked    该组已分块
Body（未分块）= Entry × Count
Body（已分块）= <<NChunks:32, <<Other:64, Rank:64>> × NChunks>>  %% 各块首条，升序
```

条目按 `(other, rank)` 升序，宽度由组标志决定：

```
Entry = <<Other:64>>                                  %% 简单图、无属性：8 B / 邻居
      | <<Other:64, Rank:64>>                         %% has_rank
      | <<Other:64, [Rank:64], PLen:16, Props/bytes>> %% has_props；PLen = 16#FFFF 表示属性在 p 家族
```

- 无属性的组条目定宽，Erlang 侧用 binary 匹配直接二分 / 批量解出，不需要 NIF。
- **入边段不存属性**（`dir = 1` 的组 `has_props` 恒 0），属性只在出边一侧存一份，
  与 v1 的 `ei` 值为空同理。
- `Count` 就是度数：`degree(Vid, Etype)` 读头即得，不再有独立计数键。
- 组标志只升不降地由写入维护；整组重写（分块 / 合并 / 迁移）时重新计算。

### 4.3 分块（hub）

参数（open-time，记入 `g`）：

- `adj_inline_max`，默认 4096 B：头的值超过它时，把最大的未分块组转为分块；
- `adj_chunk_max`，默认 4096 B：单块值上限。初次分块按字节装满切片；已有块超限时
  切成 ⌈字节 / 上限⌉（至少 2）片约等大的块（对半分裂的推广）；
- 回收：一组分块后总字节数降到 `adj_inline_max / 4` 以下时转回内联（留滞回，避免抖动）。

分块以**组**为单位：一个有 100 万入边、100 条出边的顶点，只有入边组分块，出边组
仍在头里。

```
Chunk = <<Ver:8 = 1, GFlags:8, Count:32, Entry × Count>>
```

块 key 里的 (other, rank) 是块的**下界**：块 0 恒为 (0, 0)，其后各块是建块（分块 /
分裂）时的首条。条目 e 属于下界 ≤ e 的最后一块。下界只在分裂、删空块时改变——删掉
块内首条不需要给块改名，插入比所有条目都小的条目也总有块可放（块 0）。块删空时
（块 0 除外）删 key、从目录里摘掉；整组删空时连块 0 一起删。

定位一条边：在头的块目录里找到所在块 → 点查该块 → 块内查找。写一条边 = 重写
头（度数变了，体积小）+ 重写一个块（≤ 4 KiB）。写代价不随度数增长。

块目录在头里，每块 16 B。10 万度的组约 200 块、目录 3 KiB；为了让目录保持在约
1024 项以内，超大组的实际块上限取 `max(adj_chunk_max, 组字节数 / 1024)`。度数超过
10⁷ 的顶点仍建议在建模层拆分（与 v1 的建议一致，只是门槛高了一个量级）。

### 4.4 边属性

- 不超过 `props_inline_max`（默认 128 B）：内联在出边条目里。
- 超过：写到 `p` 家族的独立 key，条目里 `PLen = 16#FFFF` 作标记；与邻接表同批原子写。
  只有带大属性的边才多一个 KV。

### 4.5 不变式

1. **对称**：`(a, t, b, r)` 在 `a` 的出边组 ⟺ 在 `b` 的入边组。任何写入都在同一个
   原子批里同时改两端。
2. **头即版本**：对一个顶点邻接的**任何**修改都重写它的头（度数在头里，必然变）。
   所以「头 key 的 LSN」就是这个顶点邻接表的版本号，包括它名下的所有块。
3. **度数 = 条目数**：`Count` 与实际条目数恒等，同批更新。
4. 头的块目录 = 实际存在的块 key；块内条目恒落在 [本块下界, 下一块下界)，同批更新。

`graphdb:check_invariants/1` 扫 `a` / `p` 家族逐条核对以上四条（外加「标 ext 的出边 ⟺
有 p 键」），测试与迁移校验都用它。

## 5. 并发：按 LSN 的条件写

### 5.1 原理

引擎每次写都分配一个 LSN（`ord`），`get` 的结果里本来就带着。v2 不在值里另存 rev，
直接把 LSN 当版本：

```
1. 读 a、b 两个顶点的头，记下各自的 LSN（不存在记为 absent）
2. 在内存里改出新值
3. 提交一个原子批，带前置条件：
     「a 头的当前 LSN 仍是我读到的那个」且「b 头的当前 LSN 仍是我读到的那个」
4. 任一条件不成立 → 整批不写，返回冲突 → 回到 1 重试
```

~~由不变式 2，只对两个头设条件就够了：块的任何变化都会带动头的 LSN 变化。批里的块
写入不需要单独设条件。~~

> **2026-11-20 更正**：这个推理默认「读者看到的头和块来自同一个已提交状态」，但 libbitcask ≤ 12.0.0
> 的原子批对并发读者**不是整批可见**——批内各 key 逐条生效，且按 key 字节序（头 key 是自己块 key 的
> 前缀，同一顶点总是头先生效、块后生效）。读者可能读到「新头 + 旧块 / 缺块」，基于它算出的写回只带头条件
> 时会成功并覆盖别人的块。上游 12.0.1（S63）已把整批发布收进一个临界区；本图层仍保留以下规则作显式防护：
> **前置条件覆盖整个读集**——改过的头、读过的每个块（改了的挂在 put / remove 上，没改的发 `check`，
> 读到缺失的用 `absent`），以及会话读过但没改的顶点的头。条件在引擎写锁内对照批前状态判断，读到的东西
> 在提交前变了就整批冲突重来；即使有人绕过图层协议直写块也不会静默覆盖。上游反馈：libbitcask
> `feedbacks/2026-11-20-atomic-batch-no-read-isolation.md`。

条件判断必须在引擎写锁内与写入原子完成，所以只能由引擎提供（§5.3）。

### 5.2 重试策略

- 直通 API 默认重试 8 次，带抖动退避；耗尽返回 `{error, conflict}`。
- 冲突只发生在「两个写者同时改同一个顶点」。不同顶点的写互不影响。
- 热点顶点（大量写者同时往一个 hub 加边）每轮只有一个成功。这类负载用批量接口
  （§6.4，按顶点聚合后一次写完）或事务层（§8，排队而不是重试）。

### 5.3 需要引擎提供的能力

详见反馈文件，摘要：

1. 原子批每个操作可带前置条件：`无` / `key 不存在` / `key 的当前 LSN == N`。
2. 全部条件在写锁内、落盘前判断；任一不成立则整批零副作用，返回专门的冲突错误，
   并指出是哪个 key。
3. 契约：一个 key 的 LSN 只在它被写入时改变——merge 搬迁、重开恢复、OKI 重建都
   不改变它。
4. 可选：批成功后返回各操作分到的 LSN，写者可以不重读就继续下一轮。

本仓库这一侧（NIF 与 Erlang 门面）落地的形态：

```erlang
bitcask:get_with_ord(H, Key)            -> {ok, Value, Ord} | not_found | {error, _}.
bitcask:put_batch_atomic(H, Ops)        %% Op 多认三种形态：
    {put,    Key, Value, Cond}          %% Value 也可以是 doc map
    {remove, Key, Cond}
    {check,  Key, Cond}                 %% 只校验不写
                                        %% Cond :: absent | {ord, N}
                                        -> ok | {error, {conflict, OpIndex}} | {error, _}.
bitcask:put_batch_atomic(H, Ops, [return_ords]) -> {ok, [Ord]} | ...   %% 各 op 的 LSN
bitcask:txn_commit(H, Ops[, Sync[, Token]])     %% 同样认带条件的 op
```

`OpIndex` 从 1 起，是 `Ops` 里的位置（由引擎 `BatchOutcome::failed_op` 映射）；拿不到
下标时兜底为 `{error, condition_failed}`。形态不认一律 `badarg`。

## 6. 写路径

### 6.1 put_edge(S, T, D, #{rank, props})

```
读 head(S)、head(D)（带 LSN）
边已存在 → 只改属性：只重写 S 一侧（头或所在块），条件只设在 head(S) 上
边不存在 →
    S 的出边组插入 (D, rank, props)，Count + 1
    D 的入边组插入 (S, rank)，Count + 1
    需要时分块 / 分裂（同批）
    原子批：[head(S) 带条件, head(D) 带条件, 涉及的块, 可能的 p 键]
自环（S = D）：同一个头里改两个组，批里只有一个头
```

### 6.2 del_edge

对称：两端各删一条、Count − 1，同批；属性在 `p` 家族的同批删掉。边不存在直接返回
`ok`（幂等，不写）。

### 6.3 del_vertex(V)

```
读 head(V) 与全部块，按邻居聚合（一个邻居可能有多条边、双向都有）
按批处理邻居（每批 ≤ 64 个邻居）：
    批内：每个邻居的头（及块）删去与 V 相关的全部条目，带条件；
          同时把 V 自己头里的这些邻居删掉，带条件
    —— 每批提交后图仍满足对称不变式，中途失败重跑即可收敛
最后一批：删 head(V)（条件：LSN 未变，保证期间没人给 V 加边）、V 的残余块、
          相关 p 键、n<V>
```

邻居数不超过一批时整个删除是单批原子的。v1 的「邻居计数器聚合 RMW」整套逻辑消失。

### 6.4 批量接口（新增）

```erlang
graphdb:put_edges(H, [{S, T, D} | {S, T, D, Opts}])  -> ok | {error, _}.
graphdb:del_edges(H, [{S, T, D} | {S, T, D, Rank}])  -> ok | {error, _}.
```

按涉及的顶点聚合：每个顶点读一次、改一次、写一次。先按 (src, etype, dst, rank) **稳定排序**（同一个 src
的边落进同一批、且落在相邻的块里，同一条边的多次 upsert 仍按调用方顺序生效；`sort => false` 关掉），再按
顶点集合切批（每批涉及的头不超过 `batch_vids` 个，默认 256），每批独立原子、独立重试。
离线装载可把 `batch_vids` 调大：整图放进一批时每个头只写一次；代价是一批越大，与并发
写者冲突时整批重来越贵。装载工具与热点顶点写入都应走这条路。

## 7. 读路径

### 7.1 原语

```
out_edges / in_edges / neighbors(V)：
    get head(V)
    组未分块 → 直接解条目
    组已分块 → 按头里的块目录逐块点读（limit 到了就停；G10 前是前缀 range）
edge(S, T, D, R)：get head(S) → 组内二分（分块则再点查一块）→ 属性若在 p 家族再点查
degree(V, T)：get head(V) → 读 Count
degree(V)：get head(V) → 各组 Count 求和（v1 是 O(出度) 扫描）
```

`limit`、`etype` 过滤在解码时完成；未分块顶点上它们不省 IO（整个值已读出，≤ 4 KiB），
分块顶点上 `etype` 下推进 range 前缀、`limit` 提前停。

### 7.2 遍历

BFS / k-hop / 双向最短路算法不变，展开一个顶点从「一次 range」变成「一次 get」。
frontier 展开可以改用批量点查，不再需要一顶点一个迭代器。

### 7.3 一致性

- 未分块顶点：一次 get 得到该顶点邻接的原子快照。
- 分块顶点：头与块分多次读。提供 `#{consistent => true}`：头与块按块目录逐个带版本点读，
  再用只含 `check` 的原子批在引擎写锁下校验读集仍是当前版本，不过则重读（2026-11-20 起；此前
  「扫描前后比头的 LSN」挡不住绕过图层协议的直写，§5.1 更正）。libbitcask 12.0.1 起在途批必然
  整批可见；该校验给 consistent 读一个写锁下的显式版本确认。只读句柄不校验。默认不开，行为与 v1
  的弱一致同档。
- 跨跳仍是弱一致，与 v1 相同。

## 8. 事务层

`put_edge_txn` 等保留，但变简单：

- 锁粒度是顶点的头 key（点锁）。约定「持有头的锁即覆盖其全部块」，**不再需要前缀锁**
  来防幻读；`out_edges_txn` 对头拿读锁即可（分块组的块按头的块目录逐块
  点读，经本事务缓冲，不拿前缀锁）。
- 事务提交时把读到的头 LSN 作为条件带进提交批。这样直通写与事务写**可以混用**：
  直通写者插进来会让事务提交冲突并重跑，而不是像 v1 那样行为未定义。落地为通用
  机制 `bitcask_txn:read_guarded/3`：读的同时登记版本，提交时写过的 key 把条件挂在
  它的 put / remove 上、只读过的 key 变成 `{check, K, Cond}`；冲突走与死锁相同的
  重跑路径与 `{retries, N}` 预算。图层的头一律经它读。
- 计数器相关的锁升级、聚合逻辑全部删除。

## 9. 其它受影响的部分

- **`edges_by_type`**：改为扫 `a` 家族的头与块、按 etype 过滤，O(V + E)。文档标明
  代价；确有高频需求时再加按 etype 开启的可选索引（另立任务）。
- **OLAP 物化（`graphdb_analytics:materialize`）**：数据已经是按顶点排好序的邻接表，
  扫一遍 `a` 家族即可直接拼出正反两个 CSR，比 v1 逐条边解析快得多。
- **属性过滤遍历、检索联动**：不变（作用在 `n` 家族上）。
- **病理 vid 防御**：v1 里 `ei` / `et` 会落进 `e` 的扫描区间；v2 的家族没有这种
  前缀包含关系（`a` 头是它自己块的前缀，属于设计内）。解析仍按长度严格校验。

## 10. 布局版本与旧数据

- `g` 键记录布局版本。打开时：有 `<G> "g"` 且版本 = 1 → 当前布局；无新 `g` 但存在旧
  的无前缀 `g` → 未加全局前缀的中间布局，返回
  `{error, graph_layout_unprefixed_v2}`；无新 `g` 但存在 `e` / `ei` 家族 → 更早的
  逐边布局，返回 `{error, graph_layout_v1}`。
- 不提供自动迁移或 `graphdb_migrate` 工具。旧图数据需要由调用方导出后重灌；
  fail-loud 的拒开检查只用于避免把旧图目录误当成空库。

### 14.2 与设计稿的出入

- 块 key 的 (other, rank) 定为块的**下界**而不是「首条」（§4.3）：删块内首条不用改名。
- `degree/2,3` 保持 v1 语义（**出度**），另加 `in_degree/2,3`；都是读头 O(1)。
- `edges_by_type` 带上属性（v1 的 `et` 键没有属性，恒返回 `<<>>`）。
- `consistent` 读最多 32 次，撞上写就带抖动退避，耗尽返回 `{error, inconsistent_read}`。
- `del_vertex` 的最后一批：顶点本来就没有邻接表时带 `{check, 头, absent}`，防止并发
  加边与删顶点交错留下悬挂边。
- `put_edges` / `del_edges` 先按 (src, etype, dst, rank) 稳定排序再切批（每批 ≤ `batch_vids`，默认 256；G10 前只按 src）。
  不排序时随机边在批内很少重复同一个顶点，聚合几乎没用；排序后 src 一侧每批只写一次，
  吞吐约 2×、字节约减半（§14.3）。
- `graph_layout_v1`：open 时探测到更早逐边布局的出边 key **且**它配对的 `ei` 反向
  key 也在才拒开（最多核对前 64 条候选），应用自己恰好有 29 字节 "e…" key 的目录
  不会误判。不提供迁移工具。
- 图层 key 统一加 `<<1,"_g:">>` 全局前缀。若目录里只有 8.0.0 中间版写的无前缀 `g`
  配置，open 返回 `{error, graph_layout_unprefixed_v2}`，避免在旧数据旁静默建一套
  新前缀数据。
- 图参数不缓存：每次写会话读一次 `g`（低度数逐条加边约慢 5–10%），换来句柄经
  `graphdb:close` 或 `bitcask:close` 关掉都不留残留、绕过 `graphdb:open` 拿到的句柄也
  按建库参数写。
- 事务里读分块组按头的块目录逐块点读，不拿前缀锁（§8）。
- 同一次写会话里新建又删掉的块不发删除（只删读到时盘上已有的块）。
- `del_vertex/3`：`retries`、`batch_neighbors => N | infinity`（infinity = 一批原子删完）。
  顶点键 `n<V>` 的删除不带条件，与并发 `put_vertex` 后写胜出（同 `bitcask:delete`）。
- 崩溃一致性没有专门的强杀测试：每次写都是一条引擎原子批，批级「全有或全无」由上游
  的崩溃恢复保证并覆盖测试。

### 14.3 基准（`test/graphdb_bench`，8 vCPU，2026-11-18）

10000 顶点 / 50000 边（幂律源，平均出度 5），三档阈值：

| 指标 | 1 KiB | 4 KiB | 16 KiB | v1 参照 |
|---|---|---|---|---|
| key 数 | 10021 | 10003 | 10000 | 169423 |
| 块数 | 21 | 3 | 0 | — |
| 灌边 put_edge（边/秒） | 71.4k | 77.4k | 69.1k | 44–88k¹ |
| 灌边 put_edges（边/秒） | 88.0k | 93.0k | 85.5k | — |
| 一跳 out_edges（ms/op） | 0.003 | 0.002 | 0.003 | ~0.02² |
| 重开后一跳（ms/op） | 0.005 | 0.004 | 0.004 | ~0.02² |
| 数据字节 / 边（put_edges） | 254 | 261 | 263 | 326 |
| 数据字节 / 边（put_edge） | 303 | 323 | 332 | 326 |
| materialize（ms） | 62 | 54 | 65 | — |

¹ v1 参照是按 v1 写法（每边一条 5 记录原子批 + 计数器读-改-写）灌的同一份边，三次
测得 44k / 44k / 88k，波动大，只作量级参考。² v1 数字取自 6.5.0 的基准记录。

2000 顶点 / 100000 边（平均出度 50，4 KiB）——§3 说的「写更贵」在这里显形：

| 指标 | v2 | v1 参照 | 比值 |
|---|---|---|---|
| key 数 | 2014（13 块） | 293187 | 1 / 145 |
| 灌边 put_edge（边/秒） | 32.8k | 91.4k | 0.36× |
| 灌边 put_edges（边/秒） | 46.2k | — | 0.51× |
| 数据字节 / 边（put_edge） | 1095 | 314 | 3.5× |
| 数据字节 / 边（put_edges） | 941 | 314 | 3.0× |
| 一跳 out_edges（ms/op） | 0.012 | ~0.02 | — |

结论：
- key 数（= keydir / OKI 常驻内存）按顶点数走：低度数图降 17×，度数 50 降 145×。
- 一跳读取一次点查，比 v1 的前缀 range 快 2–10×。
- 写：低度数时每边字节数与 v1 同档；度数 50 时每次写边重写两个约 0.5 KiB 的头，
  日志字节约 3×、单边写吞吐约 0.36×，merge 会更频繁。批量接口能挽回一部分；批内
  同顶点出现得越多收益越大，见下面「按 src 排序」一节。
- 三档阈值差别在噪声内，默认保持 4 KiB。

**按 src 排序（2026-11-18 追加）**：`put_edges` 默认先按 src 稳定排序再切批。同一份数据、
4 KiB：

| 图 | 不排序 | 排序（默认，256 顶点/批） | 排序 + `batch_vids => 4096` | v1 参照 |
|---|---|---|---|---|
| 1 万顶点 / 5 万边（度数 5）：边/秒 | 84.6k | 138.7k | 148.7k | 88.1k |
| 同上：字节 / 边 | 261 | 134 | 107 | 326 |
| 2000 顶点 / 10 万边（度数 50）：边/秒 | 42.7k | 88.6k | 253.0k | 84.3k |
| 同上：字节 / 边 | 941 | 420 | 17 | 314 |

排序后 src 的头每批只写一次，剩下的放大来自 dst 一侧（每批的 dst 各写一次）。度数 50
的批量装载由 0.51× 回到 **1.05×**，§12 的「批量装载吞吐不低于 v1」达到；整图装进一批
（2000 顶点 < 4096）时每个头只写一次，3× 于 v1、每边 17 B。单边写 `put_edge` 不受影响
（仍约 0.36–0.46×）。

**hub 路径（2026-11-23 追加，TASK G10）**：一个顶点 2 万 / 20 万条出边、4 KiB，改前 → 改后：

| 操作 | 2 万度 | 20 万度 |
|---|---|---|
| `del_vertex` | 1.11 s → 0.12 s | 450 s → 2.1 s |
| `put_edges` 装载（dst 乱序） | 0.30 s → 0.22 s | 15.3 s → 3.5 s |
| `out_edges(#{limit => 10})` | 230 µs → 13 µs | 1133 µs → 30 µs |
| `degree` | 32 µs → 5 µs | 345 µs → 18 µs |
| `edge` | 48 µs → 12 µs | 939 µs → 32 µs |
| `put_edge` | 106 µs → 67 µs | 752 µs → 255 µs |

四处改动：`del_vertex` 每轮只读够一批邻居的块（原来每轮读全部块，O(度数²)）；分块组的读改按块目录点读（原来的前缀 range
按批搬块，且每次写之后的第一次 range 要重排引擎里整个未落盘的内存增量）；读头不再为全部块 key 建表；`put_edges` 的排序键
加上 dst。剩下的代价是设计本身的：大 hub 每次写边重写整个头（20 万度时块目录约 13 KiB）。

**读路径与会话内部结构（2026-11-23 追加，TASK G11）**：读直接在头 / 块的二进制上按方向、类型挑组并一遍解出结果（不建会话
状态）；块目录在会话里保持二进制、二分定位、没变就原样写回；会话里的条目表用拉链，批内升序的插入接着上次的位置找。
20 万度 hub，上表的「改后」→ 这一轮：`put_edges` 装载 3.5 s → 0.95 s，`put_edge` 255 → 64 µs，`edge` 32 → 8.5 µs，
`degree` 18 → 4.8 µs，`out_edges(#{limit => 10})` 30 → 11 µs；`neighbors` 102 → 9.0 ms，全量 `out_edges` 57 → 43 ms。
低度数图的单跳读变化不大（`out_edges` 约 6%，`neighbors(both)` 7.5 → 4.2 µs）：一次点读本身占 2 µs。`del_vertex` 基本不变。

**单条写边（2026-11-23 追加，TASK G12）**：定宽的条目表在会话里保持盘上的二进制，单条增删二分定位后直接拼接、原样写回，
不再整块解码重编。20 万度 hub 上 `put_edge` 56 → 29 µs、`del_edge` 40 → 33 µs；度数 50 的顶点之间 29.6 → 20.5 µs；度数 5 的
图上不变（约 17 µs，其中读图参数、读两个头、原子批共约 9 µs）。
