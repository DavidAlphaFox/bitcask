# 基于 Bitcask 构建向量库 / 图库的可行性与功能清单

这是一份**设计探索**文档，回答「能不能、以及要补哪些功能，才能在当前
Bitcask 引擎之上做一个向量数据库或图数据库」。配合 `doc/cpp-arch.md`
（实现地图）、`doc/format.md`（磁盘格式）阅读。

> 结论先行：Bitcask 适合当 **持久化存储底座（KV blob 存储 + 压缩）**，
> 不适合直接当索引引擎。两个方向真正的工程量都在**索引层**和**查询层**——
> 这两层 Bitcask 完全没有，需要全新搭建。其中**向量库比图库更契合**当前
> 架构，建议先做向量库。

## 0. Bitcask 现状定位

参见 `cpp/include/bitcask/cask.hpp`、`keydir.hpp`：

- append-only 日志 + 全内存 KeyDir 哈希索引；
- `get(key)` = 一次哈希查找 + 一次 `pread`；
- `put` = 追加 data file + 改哈希表；`remove` = 写墓碑；
- 靠 `merge` 回收空间；
- 一致性快照遍历 `fold`（KeyDir 的 sibling chain + pending 机制）。

**唯一的查询模型是按精确 key 点查。** 这是后面所有取舍的根因。

| 能力 | 现状 |
|---|---|
| 点查 `get(key)` | ✅ 一次 pread |
| 顺序追加写 `put` | ✅ |
| 软删除 + merge 压缩 | ✅ |
| 一致性快照遍历 `fold` | ✅ (`CaskIter`) |
| 范围查询 / 前缀扫描 | ❌ 哈希索引天然不支持有序 |
| 二级索引 | ❌ |
| 近邻 / 相似度查询 | ❌ |
| 多 key 原子事务 | ❌ (KeyDir 注释：「get 再 put 不是原子的」) |
| 全部 key 常驻内存 | ⚠️ 既有约束，需先评估规模 |

## 1. 向量数据库需要补的功能

核心是 **ANN（近似最近邻）查询**：`search(q, k)` 返回与 q 最近的 k 个向量。

1. **向量值编解码层** — value 存 `[dim:u32][f32 × dim]` 或量化字节；
   扩展 `codec.hpp` 即可，Bitcask 现成。
2. **ANN 索引（最大工程量）** — 选型 HNSW（召回/延迟最好）或 IVF-PQ（省内存）。
   建议：**向量原始数据放 Bitcask，HNSW 图索引单独管理**（HNSW 是增量多层
   邻居图，和 append-only 日志不匹配）。索引需可从 Bitcask 全量 `fold` 重建 +
   增量 snapshot。
3. **距离度量** — L2 / cosine / dot product，SIMD 加速（本平台 x64v3 支持 AVX2）。
4. **删除处理** — 借鉴 Bitcask 的 tombstone + merge：软删 + 周期性重建索引（与 merge 同频）。
5. **metadata filtering** — 「最近 k 个且满足 category=X」，需附加属性索引层。
6. **批量插入 / 构建** — 向量库常批量灌数据后建索引，与单条 append 写模型不同。

> 取舍：HNSW 几乎必然全内存（和 KeyDir 同构，反而契合本项目气质）。
> 若向量规模超内存，需 IVF-PQ / DiskANN，属另一个量级的工程。

## 2. 图数据库需要补的功能

核心是 **遍历**：邻居、多跳、最短路、子图匹配。Bitcask 能「拿一个节点」，
做不了「拿它所有出边」。

1. **数据建模 → KV 映射**
   - 节点：`key = "v:" + node_id` → value = 属性。直接能存。
   - 边/邻接表：难点。整表存 `key="e:"+src+type` → 目标列表，则单条边增删要
     **read-modify-write 整个邻接表**，supernode 很痛；拆成独立 key
     `e:src:type:dst` 则需**前缀扫描**取邻居——而哈希索引**不支持前缀扫描**。
2. **有序 / 前缀索引（最大缺口）** — 高效取邻居需 B-tree / LSM / ART 这类
   有序索引。基本意味着要么换索引引擎，要么在 Bitcask 旁边再挂一个有序索引层。
   **这是图库比向量库更伤筋动骨之处。**
3. **遍历引擎** — BFS/DFS、k-hop、最短路，可选 Cypher/Gremlin 查询语言。纯新建。
4. **多 key 原子性 / 事务** — 加一条边要同时改 src 邻接、dst 邻接、索引；
   Bitcask 无多 key 事务，需 WAL 或上层事务协调。
5. **级联删除** — 删节点要删它所有边。

---

## 3. 两者共用、需先补的底层能力

1. **二级索引 / 有序索引框架** — 图库刚需，向量库 metadata filter 也要；
   对 Bitcask 最大的结构性扩展。
2. **多 key 事务 / 原子批量写（WAL）** — 目前完全没有。
3. **可序列化索引快照 + 崩溃恢复** — Bitcask 靠 hint file 重建 KeyDir，新索引
   需等价机制。
4. **value 大小与内存预算评估** — 向量（每条几 KB）、图 supernode 邻接表都可能
   撑爆 `max_file_size`（默认 2 GiB）和内存。
5. **查询 API 层** — 现仅 `get/put/remove/fold`，需新增 `search` / `traverse`。

---

## 4. 建议与取舍

- Bitcask 定位为 **storage engine**（value 存储 + 持久化 + 压缩），索引层独立做。
- **向量库更易落地**：HNSW 全内存索引与 KeyDir 全内存哈希同构；向量数据天然
  适合「不可变 blob + 重建索引」，契合 append-only / merge 模型。**先做向量库
  风险更低。**
- **图库瓶颈在缺有序/前缀索引与多 key 事务**，需引入有序索引引擎（或评估换底座），
  工程量更大、与现有架构冲突更多。

### 分层示意（建议形态）

```
┌─────────────────────────────────────────────┐
│  查询层   search(q,k) / traverse(start,...)   │  ← 全新
├─────────────────────────────────────────────┤
│  索引层   HNSW 图 / 有序索引(B-tree·ART) / WAL │  ← 全新，最大工程量
├─────────────────────────────────────────────┤
│  存储层   Bitcask: KV blob + merge + 恢复       │  ← 复用现有
└─────────────────────────────────────────────┘
```
